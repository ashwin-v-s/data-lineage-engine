## 1. OpenLineage

### 1.1 What is it and what problem does it solve?

OpenLineage is an open standard for lineage and metadata collection in the data ecosystem.
It defines a common event format and transport protocol so that any data tool (Airflow, Spark,
dbt, Flink, etc.) can emit lineage events in a single format, and any backend (Marquez, DataHub,
Atlan, etc.) can receive them without each pairing requiring a custom integration.

The core problem it solves: before OpenLineage, lineage capture required one bespoke integration
per (tool, backend) pair. OpenLineage replaces that N×M matrix with a single standard. It does
not compute lineage — it is a transport contract for communicating observed lineage.

Source: [openlineage.io/docs](https://openlineage.io/docs/)

---

### 1.2 Architecture

**Main components**

| Component | Description |
|---|---|
| **OpenLineage Spec** | JSON Schema defining the event payload format (OpenLineage.json / OpenLineage.yml in the repo) |
| **OpenLineage Clients** | Python, Java, Go client libraries that emit events |
| **Integrations** | Per-engine plugins (Airflow provider, Spark listener, dbt integration, Flink, etc.) that hook into execution and emit events |
| **Transport layer** | Pluggable: HTTP (POST to a backend), file (local JSON), Kafka, custom |
| **Backend** | Not part of the spec — any system can receive events. Marquez is the reference backend. DataHub, OpenMetadata, and others also implement the endpoint. |

**How data flows**

```
Pipeline execution (Airflow task / Spark job / dbt model)
        |
        v
OpenLineage integration hooks into engine lifecycle events
        |
        v
Client constructs RunEvent (or JobEvent / DatasetEvent)
        |
        v
Transport sends JSON payload to configured backend (HTTP POST to /api/v1/lineage)
        |
        v
Backend (Marquez etc.) stores, indexes and serves lineage
```

**Storage / database used**

OpenLineage itself has no storage. Storage is entirely the backend's responsibility.
Marquez uses PostgreSQL (covered in Section 2).

**APIs / services involved**

- The only defined API surface in the spec is the event payload format itself.
- Backends expose their own REST APIs for querying.
- The OpenLineage HTTP transport POSTs to a single endpoint: `POST /api/v1/lineage`.

---

### 1.3 Metadata collected

OpenLineage collects three categories of information:

**a) Job metadata**
- Namespace + name (identity)
- Type (`BATCH`, `STREAMING`, `SERVICE`)
- Source code location (via `sourceCodeLocation` facet)
- SQL text (via `sql` facet on the run)
- Documentation string

**b) Run metadata**
- `runId` (UUID, generated by the client — UUIDv7 recommended)
- `eventType`: `START`, `RUNNING`, `COMPLETE`, `ABORT`, `FAIL`, `OTHER`
- `eventTime`: ISO-8601 timestamp of the state transition
- Nominal time (scheduled time, separate from actual start time)
- Parent run reference (for nested jobs, e.g. Airflow DAG → task)
- Error message on failure

**c) Dataset metadata**
- Namespace + name (identity; namespace derived from the data source URI)
- Schema fields (column names, types)
- Data source (database instance)
- Lifecycle state change (`CREATE`, `DROP`, `ALTER`, `TRUNCATE`, `OVERWRITE`, `RENAME`)
- Dataset version (e.g. Iceberg snapshot ID)
- Data quality metrics (row count, null count, distinct count, min/max/avg — on input/output facets)
- Data quality assertions (test pass/fail results)
- Output statistics (row count, byte size written)

**Entities represented**

| Entity | Identifies as |
|---|---|
| `Job` | A reusable process definition (unique by namespace + name) |
| `Run` | One execution instance of a Job (unique by runId) |
| `Dataset` | A discrete collection of data (unique by namespace + name) |
| `DatasetField` | A column within a dataset (for column-level lineage) |

### 1.4 Runtime lineage — how it is extracted

**Mechanism**

OpenLineage extracts lineage from execution events, not from SQL parsing.
The integration hooks into the engine's execution lifecycle:

- Airflow integration: hooks into `on_task_instance_running`, `on_task_instance_success`, `on_task_instance_failed`
- Spark integration: implements `SparkListener` and intercepts `SparkListenerJobStart`, `SparkListenerSQLExecutionEnd`, etc.
- dbt integration: reads the dbt `manifest.json` and emits `JobEvent` / `DatasetEvent` (design-time, not runtime)

**Table-level lineage**

Table-level lineage is expressed as input and output dataset arrays on a RunEvent:

```json
{
  "eventType": "COMPLETE",
  "run": { "runId": "d46e465b-..." },
  "job": { "namespace": "workshop", "name": "process_taxes" },
  "inputs":  [{ "namespace": "postgres://workshop-db", "name": "workshop.public.taxes" }],
  "outputs": [{ "namespace": "postgres://workshop-db", "name": "workshop.public.unpaid_taxes" }]
}
```

The implicit rule: everything in `inputs` contributed to everything in `outputs`.
This is an observation — the system saw the job read X and write Y.

**Column-level lineage**

Column-level lineage is expressed via the `columnLineage` dataset facet on an output dataset.
Each output field declares its input fields and the transformation type:

```json
"columnLineage": {
  "fields": {
    "order_delivery_time": {
      "inputFields": [
        { "namespace": "...", "name": "delivery_7_days", "field": "order_placed_on",
          "transformations": [{ "type": "DIRECT", "subtype": "TRANSFORMATION" }] },
        { "namespace": "...", "name": "delivery_7_days", "field": "order_delivered_on",
          "transformations": [{ "type": "DIRECT", "subtype": "TRANSFORMATION" }] }
      ]
    }
  },
  "dataset": [
    { "field": "order_placed_on",
      "transformations": [{ "type": "INDIRECT", "subtype": "SORT" }] }
  ]
}
```

**Transformation types (verified from spec)**

| Type | Meaning |
|---|---|
| `DIRECT` + `IDENTITY` | Output value is the input value, unchanged |
| `DIRECT` + `TRANSFORMATION` | Output value is derived from the input value |
| `DIRECT` + `AGGREGATION` | Output is an aggregation of multiple input rows |
| `INDIRECT` + `FILTER` | Input used in WHERE clause |
| `INDIRECT` + `JOIN` | Input used in JOIN condition |
| `INDIRECT` + `SORT` | Input used in ORDER BY |
| `INDIRECT` + `GROUP_BY` | Input used in GROUP BY |
| `INDIRECT` + `WINDOW` | Input used in window function |
| `INDIRECT` + `CONDITIONAL` | Input used in IF/CASE WHEN/COALESCE |

The `masking` boolean flags cases where the input value is obfuscated (hash, count).

**SQL parsing support**

OpenLineage itself does not parse SQL. Column-level lineage is declared by the integration
(e.g. the Spark integration uses its own SQL analysis) or by the tool (dbt declares it in the manifest).
The spec defines the container format; the lineage content is whatever the producer puts there.

**What is actually captured at runtime**

What is captured: **that job J read dataset A and wrote dataset B during run R, at time T**.
What is NOT captured: whether every declared input actually contributed to every output row.
Whether `salary` contributed to `adjusted_salary` in a specific run with no US rows is not in the event.
The event records the table-level dependency. It does not record which rows or columns were active.

### 1.5 Evidence vs truth

**Is the lineage based on runtime observation?**

Yes. A RunEvent is an observation of a job's execution. It says "I observed this job
start/complete/fail, and at the time of the COMPLETE event, these were the inputs and outputs."

**What does it prove?**

- That the job ran (we have a START event).
- That the job completed normally (we have a COMPLETE event).
- That the specified datasets were read and written during that execution.

**What does it NOT prove?**

- That every input column actually influenced every output column.
- That the job completed correctly (COMPLETE means the job itself declared completion, not that the data is correct).
- That a dependency existed if no event was received. A missing event does NOT mean the job did not run — the job ran and the instrumentation failed, or the event was lost in transport.
- That two inputs both contributed to an output. If job J reads A and B and writes C, the event says A→C and B→C. It does not say which rows from A or B affected which rows in C.

**Critical point: silence is not a negative**

From the OpenLineage documentation and from our own `normalizer.py`:
```python
# Missing runtime events are NOT converted into negative evidence.
```

And from `oneuptime.com` (2026-09-08):
> "A Spark job can finish successfully while emitting no OpenLineage event.
>  The data path and the metadata path are separate."

A job that emits no COMPLETE event could mean: (a) it did not run, (b) the listener
failed to load, (c) the transport could not reach the backend, (d) the backend rejected
the payload. Absence of evidence is not evidence of absence.

### 1.7 Limitations

| Limitation | Details | Source |
|---|---|---|
| **Cartesian product problem** | In a multi-input/output job, the implicit model says every input feeds every output. A→C, A→D, B→C, B→D are all inferred even if only A→C and B→D are real. | openlineage.io/blog/explicit-lineage (2026) |
| **Column-level lineage not universal** | CLL depends on integration support. As of 2022, CLL was limited to the Spark integration and not visible in Marquez UI. Broader support has grown since, but coverage is still integration-dependent. | openlineage.io/blog/column-lineage |
| **No coverage information** | An event says "these datasets were read/written" but carries no information about which rows were evaluated, whether conditional branches were taken, or what fraction of the input was active. | spec design |
| **No negative events by design** | There is no "dataset was NOT read" event type. | spec design |
| **Instrumentation failure is silent** | A job can run and produce correct output while emitting zero events. The metadata and data paths are independent. | oneuptime.com (2026-09-08) |
| **Some operators produce no lineage** | In Airflow, operators that are "optimised" by setting state directly to SUCCESS without executing skip the task — no lineage events. | airflow.apache.org troubleshooting |
| **Streaming semantics differ** | STREAMING jobs use snapshot events with no expected terminal event. Combining accumulative batch and snapshot streaming events is not straightforward. | openlineage.io/docs/spec/run-cycle |
| **No timestamps on dataset access** | An event records the job's start/end time, not the time each individual dataset was read or written. | spec design |
| **Namespace normalization** | Namespaces are derived from physical URIs. Different tools may produce different namespace strings for the same system. | spec design |

## 2. Marquez

### 2.1 What is it and what problem does it solve?

Marquez is an open-source metadata service for the collection, aggregation, and visualization of
a data ecosystem's metadata. It is the reference backend for OpenLineage: it accepts OpenLineage
events and stores them in PostgreSQL, exposing a REST API for querying lineage graphs, run history,
dataset versions, and job versions.

It was originally built by WeWork, open-sourced in 2018, and is now an
LF AI & Data Foundation Graduated project.

Source: [github.com/MarquezProject/marquez](https://github.com/MarquezProject/marquez/blob/main/README.md)

---

### 2.2 Architecture

**Main components**

| Component | Image | Description |
|---|---|---|
| **Marquez HTTP API** | `marquezproject/marquez` | Core Java (Dropwizard) REST API, listens on port 5000 (API) and 5001 (admin) |
| **Marquez Web UI** | `marquezproject/marquez-web` | React UI, port 3000 |
| **PostgreSQL** | `bitnami/postgresql` or cloud provider | The only persistent store |
| **Scheduler** | User-provided | e.g. Airflow, sends OpenLineage events |

**How data flows**

```
OpenLineage producer (Airflow/Spark/dbt)
        |
        v
POST /api/v1/lineage  (OpenLineage event payload)
        |
        v
Marquez HTTP API receives, validates, normalises event
        |
        v
PostgreSQL: upserts namespace, job, dataset, run,
            creates/updates dataset version + job version,

        |
        v
REST queries via /api/v1/namespaces/{ns}/jobs,
                 /api/v1/namespaces/{ns}/datasets,

                 /api/v1/namespaces/{ns}/jobs/{job}/runs
```

**Storage / database used**

PostgreSQL is the only backend store. From the deployment docs:

### 2.3 Metadata model

**Entities**

| Entity | Identified by | Versioned? |
|---|---|---|
| `Namespace` | name | No |
| `Source` | name (data source connection info) | No |
| `Job` | namespace + name | Yes — job version pointer, updated on each run |
| `Run` | UUID (runId) | No — each run is its own record |
| `Dataset` | namespace + name | Yes — dataset version pointer, updated when a job writes it |
| `DatasetField` | dataset + field name | Via dataset version |
| `Tag` | name | No |

**Versioning model**

Every time a run transitions to COMPLETE, Marquez:
1. Creates or updates the output datasets.
2. Creates a new dataset version for each output — immutable snapshot of schema + run that created it.
3. Creates or updates the job version — deterministic function of (source location, context SQL, inputs, outputs).
4. Each run records which specific job version and which specific input/output dataset versions were active.

This means: given a run ID, you can reconstruct exactly what code version ran and what version of
each input it consumed. You can compare two runs and diff their job versions and input dataset versions.

This was verified by running the Marquez API walkthrough:
```
GET /api/v1/jobs/runs/{FAILED_RUN_ID}
→ latestRun.jobVersion.version  = "e9eafa5b-..."
→ latestRun.inputVersions[0].version = "a40ec54f-..."

GET /api/v1/jobs/runs/{SUCCESSFUL_RUN_ID}
→ jobVersion.version = "92d801c0-..."
→ inputVersions[0].version = "5e439f1f-..."
```
Different job version AND different input version → change in upstream code AND schema changed
(verified: `INTEGER` → `VARCHAR` in the input dataset between versions).

### 2.4 Lineage

**How lineage relationships are represented**

The lineage graph is a bipartite graph of Job nodes and Dataset nodes, with directed edges.
Every edge is either `dataset → job` (input) or `job → dataset` (output).

```json
{
  "graph": [
    {
      "id": "job:food_delivery:example.etl_delivery_7_days",
      "type": "JOB",
      "inEdges": [
        { "origin": "dataset:food_delivery:public.customers",
          "destination": "job:food_delivery:example.etl_delivery_7_days" }
      ],
      "outEdges": [
        { "origin": "job:food_delivery:example.etl_delivery_7_days",
          "destination": "dataset:food_delivery:public.delivery_7_days" }
      ]
    }
  ]
}
```

The graph can be traversed to `depth` hops from the starting node. Downstream impact analysis
is done by following `outEdges` recursively.

**What can be observed at runtime**

- Current lineage graph (latest version of every edge)
- Run history for any job
- Which dataset version each run consumed/produced
- Whether the latest run succeeded or failed
- The SQL text submitted by a run (via context facet)

---

### 2.5 Historical information

**What historical information is stored**

Marquez stores:
- All previous runs for a job (queryable via `/runs` endpoint)
- All previous job versions (queryable via `/versions/{version}`)
- All previous dataset versions (queryable via `/versions/{version}`)
- The `createdByRun` on each dataset version (which run created it)

**Can historical lineage be reconstructed?**

Partially. Given a specific run ID, you can find the exact job version and input dataset versions
active at that run. But the lineage graph endpoint (`/api/v1/lineage`) returns the **current**
graph — the latest version of each edge — not the graph as it was at a specific point in time.

**Critical gap: no as_of query**

There is no documented `as_of` or `recorded_as_of` parameter on the lineage endpoint.
The graph always reflects the latest state. If you need "what did the lineage graph look like on
2026-03-05", Marquez cannot answer that directly. You would have to manually reconstruct it
from run timestamps and version history.

This was verified by inspecting the API documentation and the `get-lineage` endpoint spec:
the only parameters are `nodeId` (required) and `depth` (integer, default 20).

No bitemporal query support exists in Marquez. This is a documented gap in our pack:
> "In our review of DataHub, OpenMetadata and Marquez, we did not find a documented
>  whole-graph historical reconstruction query with these semantics."

### 2.7 Limitations

| Limitation | Details |
|---|---|
| **No bitemporal / as_of query** | The lineage graph endpoint always returns the current state. Historical reconstruction requires manual reconstruction from version history. |
| **Latest state only on lineage graph** | `/api/v1/lineage` returns current edges. There is no parameter for "graph as of date X". |
| **No whole-graph point-in-time reconstruction** | A query equivalent to Kairos's `as_of` + `recorded_as_of` does not exist. |
| **No transaction time tracking** | Marquez has no concept of "when did Marquez first learn about this edge". `createdAt` is a creation timestamp but there is no correction or late-arrival handling. |
| **PostgreSQL only** | No other backend. Simple to operate but limits flexibility. |
| **No column-level lineage in UI** | Column-level lineage from the spec is not displayed in the Marquez UI (as of 2022 blog post; status in 2026 **TO BE VERIFIED**). |
| **Java runtime required** | The API server is Java (Dropwizard). Running it requires JVM setup. |
| **Authentication off by default** | Bearer auth is supported but disabled by default. |
| **No schema for "no event"** | If a job runs without instrumentation, Marquez has no record. There is no placeholder or warning that a run occurred without metadata. |

## 3. Ground Truth: ProvSQL and the Reference Interpreter

### 3.1 What is ProvSQL and what problem does it solve?

ProvSQL is a PostgreSQL extension for semiring provenance and uncertainty management.
It transparently rewrites SQL queries to track **which input tuples contributed to each output tuple**,
expressed as a provenance circuit. The circuits can then be evaluated in various semirings
(Boolean, counting, probabilistic, Shapley values, etc.).

For Kairos, the relevant capability is **Boolean provenance**: given a specific SQL query run on
specific data, which source tuples/columns actually contributed to each result row?
This is exactly what is needed for independent ground truth: run the benchmark SQL on benchmark data,
use ProvSQL to determine which source columns propagated to which output rows, and record that as
`PROPAGATED` or `NOT_PROPAGATED` per prediction unit.

Source: [provsql.org](https://provsql.org/)

---

### 3.2 Architecture

**How ProvSQL works**

1. Install the PostgreSQL C extension (`CREATE EXTENSION provsql CASCADE;`).
2. Add to `shared_preload_libraries` in `postgresql.conf`.
3. Query SQL normally — ProvSQL rewrites the query at the PostgreSQL planner level to track provenance circuits. No application code changes required.
4. Each output row receives a provenance token (a UUID identifying its circuit node).
5. The circuit is stored in memory-mapped files (as of the 2025 arxiv paper).
6. Evaluate the circuit in any semiring by calling ProvSQL functions on the token.

**Supported SQL constructs (verified from provsql.org)**

- INNER JOIN
- Outer joins (LEFT, RIGHT, FULL)
- Subqueries anywhere (EXISTS, IN, quantified, scalar)
- Aggregation (SUM, COUNT, MIN, MAX, AVG) with HAVING
- SET operations (UNION, INTERSECT, EXCEPT)
- CTEs (WITH)
- Recursive queries (WITH RECURSIVE)
- WHERE clauses (CASE WHEN, conditional expressions)

**What it tracks**

Given the benchmark CASE WHEN query:
```sql
CREATE TABLE out_adjusted AS
SELECT country,
       CASE WHEN country = 'US' THEN salary ELSE 0 END AS adjusted_salary
FROM employees_a;
```

For a row where `country = 'US'`: ProvSQL can determine that both `country` and `salary` contributed.
For a row where `country = 'IN'`: ProvSQL can determine that `country` contributed but `salary` did not
(the `ELSE 0` branch was taken — `salary` was not read for that row).

This is exactly the ground truth Kairos needs: did `salary` actually contribute to `adjusted_salary`
in this specific run with this specific data?

---

### 3.3 ProvSQL feasibility spike results

A feasibility spike was run on 2026-09-23. Environment: Windows, PostgreSQL 18.6.

**Result (from `research/ground_truth/SPIKE_REPORT.md`):**

The spike file is present in the repository but its result section is truncated in the version committed.
Based on the known facts:
- ProvSQL requires a C++17 compiler and the PostgreSQL development headers to build.
- ProvSQL has no pre-built Windows binary.
- PostgreSQL 18 is newer than the version ProvSQL was tested against (the README states "PostgreSQL ≥ 11").
- Building a C++ PostgreSQL extension on Windows requires MSVC or MinGW plus the PostgreSQL build tools.

**Conclusion from available evidence:** ProvSQL is not immediately usable on this Windows environment.
Installation requires either WSL2 (Windows Subsystem for Linux) or a Docker container.

This is confirmed by the presence of `reference_interpreter.py` in `research/ground_truth/` —
it is the fallback path when ProvSQL cannot be installed.

**What ProvSQL would produce if it worked (from the spec and provsql.org):**
Each output row would carry a provenance token. You call `provsql.formula(token)` or
`provsql.boolean_circuit(token)` to get a symbolic expression over the input tuple identifiers.
For the benchmark case, you would evaluate: does the token for `adjusted_salary` in a given output
row include a reference to the `salary` input tuple?

### 3.4 The Reference Interpreter (Kairos fallback)

Because ProvSQL is not available on Windows, Kairos implements `ReferenceInterpreterProvider`
in `research/ground_truth/reference_interpreter.py`.

**What it does:**

It takes an explicit `propagation_map: dict[tuple[str, str], bool]` — a manually or
programmatically computed mapping from `(source_column, target_column)` to `True/False` —
and wraps it in the `GroundTruthProvider` interface. Every determination produces a
`GroundTruthResult` with `PROPAGATED` or `NOT_PROPAGATED` and a hash of the artifact.

**How the propagation map is computed:**

For simple deterministic SQL (the benchmark subset), the map can be derived by:
1. Executing the SQL on the benchmark data.
2. Inspecting the result rows.
3. For each output row, determining which input columns influenced each output column
   (by analyzing the CASE branch taken, join conditions satisfied, etc.).
4. Recording: did `salary` appear in the computation path for `adjusted_salary` in this run?

This is manual or semi-automated. It replaces ProvSQL's circuit-based tracking with explicit
human-verified truth for the restricted SQL subset used in the benchmark.

**Independence guarantee:**

Both `ProvSQLProvider` and `ReferenceInterpreterProvider` implement `GroundTruthProvider`
(defined in `research/ground_truth/provider.py`). The CI import-boundary check verifies that
this module never imports from `ingestion`, `sqlglot`, `research.reasoning` or `research.baselines`.
Ground truth is computed independently of the prediction path.

---

### 3.5 Evidence vs ground truth: the key distinction

| | OpenLineage Runtime Evidence | ProvSQL / ReferenceInterpreter Ground Truth |
|---|---|---|
| **What it is** | An observation of execution (job ran, read X, wrote Y) | An independent determination of whether column C1 actually influenced column C2 for a specific run on specific data |
| **Produced by** | The pipeline's instrumentation, sent to Marquez | An independent execution path, never fed into the predictor |
| **What it proves** | That the job ran and accessed these datasets | Whether the dependency actually occurred at the tuple level |
| **Can be missing** | Yes — instrumentation can fail silently | Should not be missing for benchmark cases (it is our reference) |
| **Used in reasoning** | YES — the reasoning engine reads RuntimeEvidence | NO — never enters the reasoning engine |
| **Used in metrics** | Indirectly (via predictions) | YES — this is the truth the predictions are compared against |
| **Can produce negatives** | NO — a missing event is not a negative event | YES — `NOT_PROPAGATED` is a valid ground truth label |

## 4. Limitations Summary

### 4.1 OpenLineage limitations

1. **No coverage information.** Events record what was accessed, not whether conditional branches executed.
2. **Cartesian product ambiguity.** Multi-input/multi-output jobs produce over-approximated edges. The new explicit lineage facet (experimental, 2026) addresses this but is not yet finalized.
3. **Silent instrumentation failure.** A job can run correctly while producing no events.
4. **Column-level lineage is integration-dependent.** Not all integrations produce CLL.
5. **No negative events.** The spec has no "dataset was not used" event.
6. **No execution coverage.** Which rows were active, which branches were taken — not in the spec.

### 4.2 Marquez limitations

1. **No bitemporal query.** The lineage graph always returns the current state. No `as_of` parameter.
2. **No whole-graph historical reconstruction.** Point-in-time lineage graphs cannot be queried directly.
3. **No late-correction semantics.** If a run's lineage is discovered late, Marquez updates the current record but does not preserve the history of what it knew at each point.
4. **No transaction time.** `createdAt` is not a full transaction-time dimension in the bitemporal sense.
5. **Column-level lineage not displayed in UI** (verified status uncertain for 2026).
6. **Java runtime dependency.** Adds operational overhead.

### 4.3 ProvSQL limitations

1. **Not available on Windows** without WSL2 or Docker (no pre-built binary).
2. **C++ build dependency.** Requires MSVC or GCC, Boost libraries, PostgreSQL development headers.
3. **PostgreSQL ≥ 11 required.** Tested on PG 11–17; behavior on PG 18 is **TO BE VERIFIED**.
4. **Restricted SQL subset for ground truth.** For Kairos's benchmark, only deterministic SQL without outer joins is used. ProvSQL can handle more, but the ground-truth semantics for outer joins in the benchmark are an open decision (D-11 in the pack).
5. **Not available as a predictor input.** Independence boundary prevents ProvSQL output from entering the reasoning engine.

## 5. Relation to Kairos

### 5.1 What Kairos already does

| Kairos component | Counterpart in surveyed systems |
|---|---|
| `ingestion/openlineage/normalizer.py` | Equivalent to Marquez's internal OpenLineage ingestion (normalization, duplicate detection) |
| `ingestion/openlineage/etl_demo.py` | Equivalent to using an OpenLineage integration (directly emits events) |
| `research/ground_truth/provsql_provider.py` | ProvSQL as independent ground truth |
| `research/ground_truth/reference_interpreter.py` | A fallback for environments where ProvSQL cannot run |
| `contracts/evidence.py` RuntimeEvidence refusing negative construction | Enforces the "missing events are not negative evidence" rule that OpenLineage itself has no mechanism to enforce |

### 5.2 What is different

**1. Missing-event semantics are explicit in Kairos, implicit in OpenLineage/Marquez**

OpenLineage has no mechanism to distinguish "the event was not emitted because the job
did not run" from "the event was not emitted because the instrumentation failed". Kairos's
`RuntimeEvidence` cannot be constructed as a negative evaluation unless coverage is
explicitly declared complete. Marquez simply stores what it receives and is silent about
what it did not receive. Kairos makes the distinction a first-class constraint.

**2. Bitemporal storage vs single-timeline versioning**

Marquez has metadata versioning: each run records which dataset version it used.
But Marquez cannot answer "what did the lineage graph look like on date X, according to
what Marquez knew on date Y?" — the two-time-dimension query.

Kairos's PostgreSQL schema (from M3) stores both `valid_from/valid_to` (valid time) and
`transaction_from/transaction_to` (transaction time) on every edge version. This allows
exactly the queries Marquez cannot answer. Marquez's versioning covers the "what version was
active" question but not the "what did we know" question.

**3. Evidence classification vs metadata storage**

Marquez stores metadata. It does not classify evidence or assign confidence. It does not distinguish
between "we observed this dependency with full coverage" and "we inferred this dependency from a
static declaration". Kairos's evidence model tags each piece of evidence with:
- `evidence_type` (STATIC_DEPENDENCY, DBT_DECLARED, RUNTIME_POSITIVE, RUNTIME_NEGATIVE_EVALUATION)
- `parser_status` (SUPPORTED, PARTIAL, UNSUPPORTED)
- `coverage` (structured coverage vector)
- `source_system` (sqlglot, dbt_manifest, openlineage, etc.)

**4. Ground truth independence**

Neither OpenLineage nor Marquez has a concept of independent ground truth. They record what
producers declare. Kairos's architecture strictly separates the ground-truth path (ProvSQL /
ReferenceInterpreter) from the prediction path (reasoning engine). The CI import-boundary check
enforces this separation at the module level.

**5. Four-state reasoning vs binary edges**

OpenLineage and Marquez represent lineage as binary edges: the dependency either exists in
the graph or it does not. Kairos's four-state model (`OBSERVED`, `REFUTED_FOR_RUN`,
`POSSIBLE`, `UNKNOWN`) explicitly represents uncertainty and coverage gaps. `POSSIBLE` means
"static analysis says it could occur, and we have no evidence it did not." `UNKNOWN` means
"we cannot reason about this." These distinctions do not exist in OpenLineage or Marquez.

### 5.3 What Kairos can learn from OpenLineage / Marquez

**From OpenLineage:**
- The facet extensibility model is useful. Kairos's evidence records could adopt a similar
  pattern: a stable core + extensible facets for system-specific metadata.
- The transformation type taxonomy (`DIRECT`/`INDIRECT` with subtypes: IDENTITY, TRANSFORMATION,
  AGGREGATION, FILTER, SORT, CONDITIONAL) is well-designed and Kairos's static evidence
  (from SQLGlot) could be mapped to this vocabulary.
- The explicit lineage facet proposal (2026) addresses the cartesian product problem in a way
  that is directly relevant to how Kairos should handle multi-input/output jobs in its
  RuntimeEvidenceProvider: record precise input→output mappings where known, not a cartesian product.

**From Marquez:**
- The run versioning model (deterministic job version fingerprint + input/output dataset versions
  per run) is a good pattern for Kairos's `execution_run` and `evidence` tables. Knowing which
  dataset version each run consumed enables the "what was the data at the time of this run" query.
- The `createdByRun` linkage on dataset versions is useful for tracing dataset provenance forward
  and backward without graph traversal.
- The bipartite graph representation (Job nodes + Dataset nodes + directed edges) is exactly
  Kairos's lineage graph model. The `nodeId` query format (`job:<ns>:<name>`) is a reasonable
  API surface to adopt for Kairos's lineage endpoint.

**From ProvSQL:**
- The circuit-based provenance model is theoretically the cleanest way to establish ground truth
  for the benchmark. When ProvSQL becomes available (Linux/Docker), it should be used over the
  reference interpreter for anything beyond simple CASE WHEN queries.
- The `WHERE`-provenance mode (which source cells influenced which output cells) is exactly what
  the benchmark needs for column-level ground truth. Kairos should document this as the target
  capability once ProvSQL is installable.

### 5.4 Open questions for Kairos from this research

1. **ProvSQL on Windows / Docker**: The spike failed on native Windows. A Docker-based setup
   should be attempted. If Docker is available, `docker run -e POSTGRES_PASSWORD=kairos postgres:16`
   + installing the ProvSQL extension inside the container would resolve the platform dependency.
   This is the most important unresolved item for the ground-truth path.

2. **Coverage vector from OpenLineage events**: OpenLineage events carry no coverage information.
   Kairos's `evidence.coverage` field requires a structured coverage vector. For runtime evidence
   derived from OpenLineage, the coverage must be inferred from the event structure (e.g. "COMPLETE
   event received = dataset-level coverage confirmed") or left as incomplete. Decision D-09 in the pack
   covers this and remains open.

3. **Negative evaluation semantics**: `RUNTIME_NEGATIVE_EVALUATION` evidence requires the
   coverage to be complete and runtime-mode. OpenLineage COMPLETE events prove the job ran and
   the datasets were accessed, but they do NOT prove column-level coverage. Therefore, column-level
   REFUTED_FOR_RUN can only be asserted if the integration provides column-level coverage information.
   Table-level REFUTED_FOR_RUN would require a different coverage model. This interacts with D-10
   (what counts as positive runtime evidence) and D-11 (ground truth semantics).

4. **Marquez as a reference backend**: The team could run Marquez locally via Docker to observe
   exactly what OpenLineage events look like when stored and queried. This would give a concrete
   view of what Kairos's own API should return — and confirm the gaps (no bitemporal query).
