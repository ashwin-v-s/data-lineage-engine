# Competitor analysis: how freshness monitoring actually works

Yes—competitors run freshness checks **on a schedule**, but they do not necessarily scan the entire source constantly. They define three things:

```text
1. What signal proves the data changed
2. How often to check that signal
3. How long is too long since the last update
```

That is the exact model Kairos should use.

## 1. The universal freshness model

```text
Asset has an expected update pattern
  → Platform checks a freshness signal on a schedule
  → Platform compares last observed change with the allowed window
  → If too old: mark late/stale, raise incident, notify owner
  → If updated: mark healthy and record evidence
```

| Component | Meaning | Example |
| --- | --- | --- |
| Freshness signal | Proof that data changed | `updated_at`, OpenLineage run, audit log, row-count change |
| Evaluation schedule | How often Kairos checks | Every 15 minutes, hourly, daily, CRON |
| Lookback / change window | How far back to look for a change | Last 6 hours, since previous check |
| Freshness SLA | Maximum acceptable age | Data must be no older than 24 hours |
| Freshness result | Current state | Healthy, at risk, late, stale, unknown |

## 2. DataHub

DataHub calls this a **Freshness Assertion**: a configurable data-quality rule that determines whether a warehouse table has been updated within a given period. [docs.datahub](https://docs.datahub.com/docs/managed-datahub/observe/freshness-assertions)

It has two key settings:

| Setting | Meaning |
| --- | --- |
| Evaluation schedule | How often DataHub checks the table |
| Change window / lookback | How far back it looks for evidence of change |

DataHub says the evaluation schedule should normally match the table’s expected change frequency: hourly tables are checked hourly; daily tables are checked daily. It also supports more frequent checks to detect staleness sooner. [docs.datahub](https://docs.datahub.com/docs/managed-datahub/observe/freshness-assertions)

### DataHub freshness signals

DataHub supports multiple evidence sources, depending on the data platform:

| Signal | How it detects freshness |
| --- | --- |
| Audit log | Reads platform operational/audit logs for table changes |
| Information schema | Reads system metadata tables |
| Last-modified column | Queries a column such as `updated_at` |
| High-watermark column | Checks for a new maximum value in an increasing column |
| DataHub operation | Uses an operation event reported to DataHub |

DataHub can issue a query against the table to look for rows modified within the configured window, or use a high-watermark column to detect a new maximum value. [docs.datahub](https://docs.datahub.com/docs/managed-datahub/observe/freshness-assertions)

### Example

```yaml
lookback_interval: "6 hours"
last_modified_field: updated_at
schedule:
  type: interval
  interval: "6 hours"
```

This checks every 6 hours whether `purchase_events` has rows with `updated_at` within the last 6 hours. [docs.datahub](https://docs.datahub.com/docs/assertions/open-assertions-spec/)

### Kairos lesson

Kairos should support:

- `updated_at` / last-modified column.
- High-watermark column.
- OpenLineage operation event.
- Information-schema/catalog metadata.
- Configurable evaluation schedule.
- Configurable lookback window.

## 3. Monte Carlo

Monte Carlo offers two freshness monitor types:

1. **Time since last update**
2. **Time since last row-count change** [docs.getmontecarlo](https://docs.getmontecarlo.com/docs/freshness)

It supports:

| Configuration | Behavior |
| --- | --- |
| Automatic thresholds | Learns normal update patterns and alerts on unusual delay |
| Explicit threshold | User defines how often data should update |
| Periodic check | Runs at a fixed interval |
| Scheduled check | Runs at specific times |
| CRON check | Runs using a custom CRON expression |

Monte Carlo automatically chooses a check frequency that ensures it can detect a breach; for example, if data must update at least every 6 hours, it checks often enough not to miss a violation. [docs.getmontecarlo](https://docs.getmontecarlo.com/docs/freshness)

### Example

A table is expected to update daily at 7:40 AM, with an internal deadline of 8:00 AM. Monte Carlo can run at 7:55 AM and create an incident/notification if the expected job has not completed. [docs.getmontecarlo](https://docs.getmontecarlo.com/docs/freshness)

### Freshness rules

Monte Carlo’s Freshness Rules periodically collect target-table metadata to determine whether the table has received an expected update. It recommends matching the check schedule and lookback range to the actual run schedule—for example, run every 6 hours with a 6-hour lookback, or run daily at 9 AM with a 2-hour lookback for a scheduled morning job. [docs.getmontecarlo](https://docs.getmontecarlo.com/docs/freshness-rules)

### Kairos lesson

Kairos should support:

- Time since last update.
- Time since last row-count change.
- Automatic/learned thresholds later.
- Explicit SLA threshold now.
- Fixed interval, daily-time, and CRON schedules.
- Incident creation and owner notification on breach.

## 4. OpenMetadata

OpenMetadata has a built-in test called **“Table Data to Be Fresh.”** It validates whether a table’s data is fresh using a freshness column and a maximum allowed time since update. [docs.open-metadata](https://docs.open-metadata.org/v1.11.x/how-to-guides/data-quality-observability/quality/test)

Its rule is simple:

```text
If time_since_update > timeSinceUpdate → FAIL
If time_since_update <= timeSinceUpdate → SUCCESS
```

For example, if `timeSinceUpdate` is 86,400 seconds, the table must have been updated within the last 24 hours. [docs.open-metadata](https://docs.open-metadata.org/v1.13.x/how-to-guides/data-quality-observability/quality/tests-yaml)

### Scheduling

OpenMetadata runs tests through a pipeline. The user adds a pipeline, sets the desired frequency/time zone, submits it, and the tests run on that schedule. Results then appear in the Data Quality tab. [docs.open-metadata](https://docs.open-metadata.org/v1.11.x/how-to-guides/data-quality-observability/quality/test)

OpenMetadata data contracts can also link quality test cases to a contract; saving a contract creates a test suite and pipeline that runs it. Contract validation runs daily at midnight by default, though the schedule can be changed. [docs.open-metadata](https://docs.open-metadata.org/v2.0.x/how-to-guides/data-contracts/spec)

### Kairos lesson

Kairos should treat freshness as a **quality assertion**:

```text
Assertion: revenue_daily must be fresh within 24 hours
Freshness column: updated_at
Evaluation schedule: hourly
Failure action: create/update incident
```

## 5. Atlan

Atlan’s model is active metadata: connector-driven metadata extraction plus governance context propagation. When source metadata or governance classifications change, Atlan can propagate context—such as PII classifications—through lineage. 

For freshness specifically, Atlan relies on connector ingestion and metadata refresh rather than exposing the same low-level freshness-assertion configuration as DataHub or Monte Carlo. The exact behavior depends on the connector, source permissions, and product edition. `INFERENCE`

### Kairos lesson

Do not claim Atlan-style continuous freshness for every source. Instead, make freshness capability source-specific:

```text
PostgreSQL catalog → metadata sync freshness
OpenLineage source → runtime freshness
dbt artifact → artifact/run freshness
GitHub source → commit/file freshness
```

## 6. How Kairos should implement it

### Freshness configuration

```json
{
  "asset_urn": "kairos:table:finance:analytics.revenue_daily",
  "freshness_sla": "24h",
  "evaluation_schedule": "0 * * * *",
  "lookback_window": "24h",
  "freshness_signal": {
    "type": "openlineage_run | updated_at_column | high_watermark | source_metadata | manual",
    "column": "updated_at",
    "source": "postgres"
  },
  "incident_policy": {
    "create_on_late": true,
    "notify_owner": true,
    "severity": "high"
  }
}
```

### Evaluation logic

```text
At every scheduled run:

1. Get asset freshness configuration
2. Get latest freshness evidence
3. Calculate:
     age = now - last_successful_update_at
4. Compare age with freshness_sla
5. Set state:
     age <= 80% SLA → HEALTHY
     age > 80% SLA and <= SLA → AT_RISK
     age > SLA → LATE
     no reliable evidence → UNKNOWN
6. Create/update incident if LATE
7. Notify owner
8. Store freshness result and evidence
9. Update UI through refetch or Supabase Realtime
```

### Freshness states

| State | Rule |
| --- | --- |
| `HEALTHY` | Last successful update is within SLA |
| `AT_RISK` | Approaching SLA breach, e.g. over 80% of SLA elapsed |
| `LATE` | SLA exceeded |
| `STALE` | No update for a much longer period, e.g. multiple SLA windows |
| `UNKNOWN` | No reliable freshness evidence exists |
| `PAUSED` | Monitoring intentionally disabled |

## 8. Important correctness rule

Do **not** mark an asset late merely because Kairos has not received an event.

| Situation | Correct freshness state |
| --- | --- |
| OpenLineage confirms update 2 hours ago | `HEALTHY` |
| `updated_at` shows update 2 hours ago | `HEALTHY` |
| No freshness evidence exists | `UNKNOWN` |
| Last known update was 30 hours ago; SLA is 24 hours | `LATE` |
| Event missing but coverage is incomplete | `UNKNOWN`, not automatically late/refuted |
| User manually confirms refresh | `HEALTHY`, with manual evidence provenance |

This preserves Kairos’s evidence-first principle: absence of evidence is not proof of failure.

> **Kairos evaluates freshness on a configurable schedule. Each asset defines an expected update frequency and freshness SLA. Kairos checks evidence from OpenLineage runs, dbt results, source metadata, high-watermark columns, or manual refresh confirmations. If the latest observed update exceeds the SLA, Kairos marks the asset late, creates or updates an incident, notifies the owner, and records the freshness result as evidence.**

This matches the competitor pattern: DataHub uses freshness assertions with evaluation schedules and change windows; Monte Carlo uses freshness monitors with explicit or learned thresholds; OpenMetadata uses scheduled freshness test cases. [docs.datahub](https://docs.datahub.com/docs/managed-datahub/observe/freshness-assertions)




Yes—**Kairos should run freshness checks on a schedule**, but it should not necessarily “constantly” poll every source. The correct model is:

```text
Freshness check = scheduled evaluation of whether an asset updated within its expected SLA
Source sync     = scheduled discovery/ingestion of metadata from the source
Realtime update = immediate UI notification after an internal Kairos change
```

These are three different jobs.

## How freshness works

For every important asset, Kairos stores a freshness expectation:

```json
{
  "asset_urn": "kairos:table:finance:analytics.revenue_daily",
  "freshness_sla": "24h",
  "expected_update_frequency": "daily",
  "last_successful_update_at": "2026-10-31T02:00:00Z",
  "next_expected_update_by": "2026-11-01T02:00:00Z",
  "freshness_status": "healthy"
}
```

Then a scheduled worker runs periodically:

```text
Every 15 minutes / hourly:
  → Find assets with freshness SLAs
  → Read latest successful update/run/event
  → Compare elapsed time with SLA
  → Set status:
      HEALTHY
      AT_RISK
      LATE
      STALE
      UNKNOWN
  → Create/update incident if SLA breached
  → Notify owner
  → Update UI
```

## Freshness states

| State | Meaning | Example |
| --- | --- | --- |
| `HEALTHY` | Updated within SLA | Last update 2 hours ago; SLA is 24 hours |
| `AT_RISK` | Approaching SLA breach | Last update 20 hours ago; SLA is 24 hours |
| `LATE` | SLA breached | Last update 30 hours ago; SLA is 24 hours |
| `STALE` | No update for a long period | No update for 7 days |
| `UNKNOWN` | No reliable update timestamp or run evidence | Source does not expose update time |
| `PAUSED` | Freshness monitoring intentionally disabled | Non-production asset |

Important: if Kairos has no update timestamp or run evidence, it must show `UNKNOWN`, not falsely mark the asset healthy or late.

## How often should it run?

| Asset importance | Freshness check frequency | Source sync frequency |
| --- | --- | --- |
| Critical / certified / production | Every 5–15 minutes | Every 1–6 hours |
| Standard production | Every 30–60 minutes | Every 6–24 hours |
| Internal / non-critical | Every 6–24 hours | Daily |
| Experimental / demo | Manual or daily | Manual |
| Real-time pipeline source | Event-driven via OpenLineage | Event-driven |

For your MVP, start with:

## What triggers freshness change?

| Event | Freshness result |
| --- | --- |
| OpenLineage run reports successful output | Asset last-updated time advances |
| dbt run result succeeds | Model freshness advances |
| PostgreSQL sync sees updated table | Table freshness advances, if source timestamp is available |
| GitHub commit changes a SQL/dbt file | File freshness advances |
| User manually marks asset refreshed | Freshness advances, with `MANUAL` provenance |
| No new run/event arrives | Elapsed time grows; status may become `AT_RISK`, `LATE`, or `STALE` |
| No timestamp exists | Status remains `UNKNOWN` |

## Important rule

Freshness must be evidence-based:

```text
Do not say “fresh” just because the catalog row was recently updated.
Do not say “late” just because Kairos has not received an event.
```

Instead:

| Situation | Correct freshness state |
| --- | --- |
| OpenLineage confirms successful output 2 hours ago | `HEALTHY` |
| Source catalog shows `updated_at` 2 hours ago | `HEALTHY` |
| No update timestamp available | `UNKNOWN` |
| Last known update was 30 hours ago and SLA is 24 hours | `LATE` |
| Event missing but coverage incomplete | `UNKNOWN`, not automatically late/refuted |
| User manually confirms refresh | `HEALTHY`, with manual evidence provenance |

## MVP recommendation

Build freshness in this order:

1. Add `freshness_sla`, `last_successful_update_at`, `freshness_status`, and `freshness_checked_at` to assets.
2. Run a scheduled freshness evaluator every 15 minutes or hourly.
3. Update freshness from OpenLineage run events first.
4. Update freshness from dbt run results second.
5. Update freshness from PostgreSQL source metadata third.
6. Create an incident when an asset becomes `LATE`.
7. Show a freshness trend chart in the Quality tab.
8. Use Supabase Realtime only to refresh the UI after the database changes.

## Poster / demo wording

> **Kairos runs scheduled freshness evaluations against each asset’s defined SLA. Runtime events from OpenLineage, dbt results, source metadata synchronization, and manual refresh confirmations update the last-known successful update time. If an asset exceeds its freshness SLA, Kairos changes its freshness state, creates or updates an incident, notifies the owner, and reflects the change in the Quality dashboard.**

Do not claim “real-time monitoring” unless OpenLineage or another event producer is actually connected and tested. For the MVP, say **“scheduled freshness monitoring with event-driven updates where available.”**




## Short answer

The system does **not** automatically know about every external change by magic. There are only three ways a metadata platform learns that something changed:

1. **Pull / polling** — Kairos periodically reconnects to the source and checks for changes.
2. **Push / event** — the source actively sends Kairos an event when something changes.
3. **Internal database change capture** — when a change happens inside Kairos’s own Supabase PostgreSQL, Supabase Realtime can notify open browser sessions.

Competitors use different combinations of these. Kairos should use all three, but with clear boundaries.

## 1. The three update mechanisms

| Mechanism | How it works | Example | Latency | Reliability |
| --- | --- | --- | --- | --- |
| Pull / scheduled crawl | Kairos connects to source on a schedule and compares metadata | PostgreSQL catalog scan every 6 hours | Minutes/hours | Reliable if scheduled and retried |
| Push / webhook | Source calls Kairos when an event occurs | GitHub push, OpenLineage event, dbt run | Seconds | Reliable only with signature, retry, idempotency |
| Internal CDC / Realtime | Kairos database change is streamed to open UI clients | User A imports asset; User B’s catalog updates | Seconds | UI delivery; not a guaranteed workflow queue |

## 2. How competitors do it

### DataHub

DataHub supports both **pull-based** and **push-based** ingestion.

```text
Pull-based:
Connector crawls Snowflake / BigQuery / dbt / Airflow / Looker
  → extracts metadata
  → sends Metadata Change Proposal to Kafka or HTTP
  → DataHub applies it to metadata graph

Push-based:
Airflow / Spark / Great Expectations emits metadata event
  → SDK sends Metadata Change Proposal
  → DataHub updates graph in near real time
```

DataHub’s ingestion framework explicitly supports push, pull, asynchronous, and synchronous models. Pull-based integrations crawl sources on a schedule; push-based integrations emit metadata changes from the point of origin through Kafka or HTTP. [docs.datahub](https://docs.datahub.com/docs/architecture/metadata-ingestion)

DataHub’s internal architecture is streaming-first: metadata changes are communicated through Kafka and reflected in the platform within seconds. [docs.datahub](https://docs.datahub.com/docs/introduction)

**Kairos lesson:** use scheduled pulls for database/catalog sources and push events for pipelines/dbt/OpenLineage.

### OpenMetadata

OpenMetadata uses a scheduled metadata agent/connector.

```text
Admin creates connector
  → Configures source connection
  → Selects schedule: hourly / daily / weekly / custom
  → Sets retries
  → Deploys ingestion pipeline
  → Agent runs and ingests metadata
  → UI shows queued / running / failed / successful status
```

OpenMetadata documents that users add a connector and schedule metadata fetches at a preferred frequency. It also supports retry counts, debug logs, deleted-table handling, query-parsing timeout, and agent run history. [docs.open-metadata](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/how-to-guides/admin-guide/how-to-ingest-metadata)

**Kairos lesson:** every connector needs a visible ingestion-run history, schedule, retry count, and failure state.

### Atlan

Atlan uses connector-driven metadata extraction and active metadata propagation. When governance context such as PII classification changes, it can propagate through lineage to downstream assets. 

**Kairos lesson:** when a source metadata change occurs, Kairos should not only update the asset—it should recompute affected lineage, PII propagation, impact, and contract status.

### Supabase Realtime

Supabase Realtime listens to PostgreSQL changes through logical replication/WAL and broadcasts them to subscribed browser clients over WebSockets. [atlan](https://atlan.com/active-data-governance/)

```text
User A imports asset
  → Kairos API inserts into Supabase PostgreSQL
  → PostgreSQL WAL records INSERT
  → Supabase Realtime reads replication stream
  → Authorized subscribed clients receive event
  → User B’s open Catalog page updates
```

Supabase Realtime supports `INSERT`, `UPDATE`, `DELETE`, or all events, with server-side filters. [supabase](https://supabase.com/docs/reference/self-hosting-realtime/introduction)

**Important limitation:** Supabase explicitly says Postgres Changes does **not yet guarantee delivery of every change**. WAL buildup, replication lag, crashes, or disconnection can cause missed events. [atlan](https://atlan.com/active-data-governance/)

**Kairos lesson:** use Realtime for live UI refresh, not as the authoritative event queue.

## 3. How Kairos should detect changes

### A. Changes inside Kairos

Example: User A imports an asset, edits a description, tags PII, resolves an incident, or creates a lineage edge.

```text
User action
  → Kairos API validates authorization
  → Writes to Supabase PostgreSQL
  → Creates an internal change event
  → Updates affected projections
  → Realtime notifies authorized open clients
  → Other users refetch or update UI
```

Use Supabase Realtime for:

- New/updated asset in Catalog.
- New lineage edge.
- PII classification change.
- Incident status change.
- Quality result change.
- Connection health change.

But always re-fetch authorized data from the API; do not trust the Realtime payload alone for authorization or complete state.

### B. Changes in an external PostgreSQL source

Kairos cannot use Supabase Realtime to watch the user’s external PostgreSQL database unless that database is configured for logical replication and Kairos has permission to consume it. That is too complex for the MVP.

Use **scheduled pull**:

```text
Every 6 hours / daily:
Kairos connector connects to user PostgreSQL
  → reads catalog metadata
  → compares with last snapshot
  → creates new/updated/deleted asset events
  → normalizes and persists changes
  → updates catalog and lineage projections
```

Track:

```text
last_full_sync_at
last_incremental_sync_at
sync_cursor
source_snapshot_hash
records_created
records_updated
records_deleted
records_failed
```

### C. Changes in GitHub

Use GitHub webhooks or scheduled polling.

```text
Preferred:
User installs Kairos GitHub App
  → Selects repository
  → GitHub sends push event to Kairos webhook
  → Kairos verifies signature
  → Kairos fetches changed files/tree
  → Parses SQL/dbt/OpenLineage artifacts
  → Updates assets and lineage evidence

Fallback:
Kairos polls repository every 15 minutes / hourly
  → Compares latest commit SHA
  → Fetches only changed files
```

GitHub Apps can receive webhooks, and GitHub recommends verifying webhook payloads with a webhook secret and requesting only minimum permissions. 

### D. Changes from dbt

dbt does not continuously push changes by itself. Kairos should ingest artifacts when they are produced.

```text
dbt run / dbt build completes
  → CI/CD or user uploads manifest.json / run_results.json
  → OR CI sends artifact to Kairos webhook
  → Kairos parses models, tests, dependencies, results
  → Updates declared lineage and quality evidence
```

`manifest.json` gives declared dependencies; `run_results.json` gives execution/test outcomes. They are different evidence types.

### E. Changes from OpenLineage

This is the best push-based source.

```text
Pipeline runs
  → OpenLineage emitter sends event to Kairos webhook
  → Kairos validates signature/schema
  → Stores immutable raw event
  → Normalizes job/run/dataset/facets
  → Updates run evidence and lineage
  → Notifies affected asset owners
```

OpenLineage events are designed for exactly this: they carry job, run, inputs, outputs, event time, producer, and extensible facets.

## 5. What should trigger an automatic update?

| Change | Kairos reaction |
| --- | --- |
| New asset discovered | Create canonical asset; update catalog count; notify workspace |
| Asset renamed | Preserve URN if stable source ID exists; record rename event |
| Column added/removed | Update schema; evaluate affected column lineage |
| Column type changed | Create schema-drift evidence; assess downstream impact |
| New dbt model dependency | Create declared lineage edge with `POSSIBLE` state |
| dbt test fails | Create/update quality result and incident |
| OpenLineage run succeeds | Create run evidence; upgrade matching `POSSIBLE` edges to `OBSERVED` only where justified |
| OpenLineage event missing | Do **not** create refutation; keep `UNKNOWN`/`POSSIBLE` |
| PII tag added | Propagate classification through lineage; notify steward |
| Connection credential expires | Mark connection `CREDENTIALS_EXPIRED`; stop sync; notify owner |
| Source deleted/disconnected | Mark connection state; decide retention policy |
| User edits description | Create metadata-version history; update search index |
| User resolves incident | Record actor, time, reason, and evidence |

## 6. What Kairos must never do

| Wrong behavior | Correct behavior |
| --- | --- |
| Assume no OpenLineage event means no dependency | Mark `UNKNOWN` or keep `POSSIBLE` |
| Automatically create lineage from two similar table names | Require parser, manifest, event, or explicit user declaration |
| Treat credential success as discovery success | Track each lifecycle stage separately |
| Use Supabase Realtime as the only ingestion mechanism | Use durable queue + immutable raw-event ledger |
| Broadcast all metadata changes to all users | Apply RLS/workspace authorization before delivery |
| Overwrite historical evidence | Append new evidence and preserve temporal history |
| Silently refresh UI from an unauthorized Realtime payload | Refetch through authorized API |

## 7. MVP recommendation

For Kairos’s first reliable demo:

| Change type | Mechanism |
| --- | --- |
| User imports JSON/dbt/OpenLineage | Immediate API write + UI refetch |
| Another user has page open | Manual refresh first; Supabase Realtime later |
| User PostgreSQL source | Scheduled pull every 6–24 hours |
| GitHub source | Manual “Sync now” first; webhook later |
| dbt artifact | Upload or CI webhook |
| OpenLineage | Webhook or deterministic event upload |
| PII/lineage/quality change inside Kairos | Supabase Realtime notification + authorized refetch |

Do **not** build continuous CDC from external user databases in the MVP. It requires source-side replication permissions, WAL management, and operational complexity that are unnecessary for a credible student demo.

## 8. Final architecture statement

> Kairos detects changes through three complementary mechanisms: scheduled pull-based discovery for external databases and repositories, push-based webhooks for dbt and OpenLineage events, and Supabase Realtime for propagating authorized internal PostgreSQL changes to open user sessions. Every external change is stored as immutable raw evidence, normalized into canonical assets and relationships, and evaluated through Kairos’s four-state evidence model. Supabase Realtime improves UI freshness but is not the authoritative ingestion queue; PostgreSQL remains the single source of truth.

This matches the industry pattern: DataHub uses pull and push ingestion with streaming propagation; OpenMetadata uses scheduled ingestion agents; Supabase Realtime provides database-change streaming for UI updates. [docs.datahub](https://docs.datahub.com/docs/architecture/metadata-ingestion)


# Supabase + competitor analysis: what Kairos should do

## Direct answer

**Do not drop PostgreSQL.** Supabase **is PostgreSQL**—every Supabase project provides a full PostgreSQL database, not a Postgres abstraction. Supabase adds Auth, Storage, Realtime, Edge Functions, and vector support around that database. [supabase](https://supabase.com/docs/guides/database/overview)

So Kairos should use:

```text
PostgreSQL = authoritative metadata/evidence database
Supabase   = managed hosting + Auth + RLS + Storage + Realtime + Edge Functions
Neo4j      = optional rebuildable projection only; do not add now
```

Your original architecture remains valid. You are not replacing PostgreSQL with Supabase; you are hosting PostgreSQL on Supabase. [supabase](https://supabase.com/docs/guides/database/overview)

## 4. What competitors do that Kairos should copy

### A. Central metadata store

All mature platforms separate:

```text
Raw source evidence
  → normalized metadata
  → canonical assets
  → derived lineage/search projections
```

DataHub uses multiple synchronized stores because it needs full-text search, graph traversal, SQL-like queries, and key-value/document lookup at scale.  Kairos does not need that complexity yet. [atlan](https://atlan.com/linkedin-datahub-tutorial/)

**Kairos decision:** keep PostgreSQL authoritative; add materialized views/read models only when queries become slow.

### B. Capability-aware UI

OpenMetadata changes asset tabs by resource type: tables get schema/sample data/queries/profiler/quality; pipelines get executions; ML models get features. 

**Kairos decision:** the backend must return a capability registry:

```json
{
  "schema": { "supported": true, "available": true },
  "preview": { "supported": true, "available": false, "reason": "No preview data retrieved" },
  "lineage": { "supported": true, "available": false, "reason": "No lineage evidence ingested" },
  "quality": { "supported": false, "available": false, "reason": "Unsupported resource type" }
}
```

Never show a tab as functional when its backing capability does not exist.

### C. Connector lifecycle

Atlan and OpenMetadata separate connection configuration, authentication, connection testing, discovery, ingestion, scheduling, and failure handling. 

**Kairos decision:** track these states separately:

```text
CONFIGURED
AUTHENTICATED
REACHABLE
AUTHORIZED
DISCOVERY_IN_PROGRESS
DISCOVERY_COMPLETED
NORMALIZED
PERSISTED
REFRESH_IN_PROGRESS
STALE
SYNC_FAILED
CREDENTIALS_EXPIRED
REVOKED
```

A successful credential test does **not** mean discovery succeeded.

### D. Evidence-first lineage

OpenLineage stores jobs, runs, datasets, events, and facets. Its lineage facets can describe exact datasets, jobs, and fields from which a dataset derives. 

**Kairos decision:** every lineage edge must have evidence:

```text
Raw event / SQL parse / dbt manifest / manual action
  → evidence record
  → relationship
  → four-state conclusion
  → UI explanation
```

### E. Permission-aware metadata access

Atlan separates users, groups, personas, purposes, connection access, visibility, and audit logs.  Supabase uses JWT identity plus PostgreSQL RLS to enforce access from browser to database. 

**Kairos decision:** use two separate authorization layers:

```text
Source credential → what Kairos backend may read from user’s source
Kairos RLS/role   → which Kairos user may see imported metadata
```

Supabase provides authentication, row-level security, file storage, realtime updates, Edge Functions, and vector-search infrastructure around PostgreSQL. The platform does not replace PostgreSQL with Supabase; it uses Supabase to operate and secure its PostgreSQL database.**

Do **not** migrate to Firebase, MongoDB, Appwrite, or Neo4j now. Keep Supabase PostgreSQL as the single source of truth, add proper RLS/workspace isolation, and use derived projections only when performance requires them. This matches the simpler PostgreSQL-plus-search architecture used by OpenMetadata and avoids DataHub’s multi-store operational complexity while preserving Kairos’s evidence-first differentiation. [supabase](https://supabase.com/docs/guides/database/overview)




Correct—but with one important correction: **Supabase does not magically make PostgreSQL “different.” Supabase is simply PostgreSQL running in the cloud, shared by your application.**

## The real difference

| Setup | Where data lives | Who sees changes |
| --- | --- | --- |
| Local PostgreSQL on your laptop | Only your machine | Only you, unless others connect to your machine |
| Supabase PostgreSQL | Cloud database used by the deployed Kairos app | Every Kairos user/API request using that same Supabase project |
| Local PostgreSQL exposed to internet | Your machine, but shared if configured | Anyone authorized to connect |
| Supabase + Realtime | Cloud PostgreSQL + WebSocket updates | Users can see changes without manual refresh |

So yes: if User A imports an asset through the deployed Kairos app, and the app writes it to the same Supabase PostgreSQL database, then User B can see it after querying the catalog—because they are both reading the **same central database**.

```text
User A → Kairos app → Supabase PostgreSQL
User B → Kairos app → same Supabase PostgreSQL
```

## But Supabase does not automatically update every screen

A database change does not automatically appear in another user’s already-open browser unless you implement one of these:

| Mechanism | Behavior |
| --- | --- |
| Manual refresh / refetch | User sees updated data next time the page or view loads |
| Polling | Frontend periodically refetches catalog/lineage |
| Supabase Realtime | Database change event is pushed to subscribed clients |
| WebSocket / SSE | Backend pushes a custom update event |
| Cache invalidation | Frontend refetches after a mutation or invalidation signal |

Supabase Realtime can listen to PostgreSQL `INSERT`, `UPDATE`, and `DELETE` events and deliver them to subscribed clients over WebSockets. But it should be used for UI updates, not as the guaranteed queue for ingestion or lineage processing. [supabase](https://supabase.com/blog/realtime-or-pipelines-how-to-choose-the-right-tool)

## Correct Kairos behavior

```text
User A imports asset
  → Kairos API validates and writes to Supabase PostgreSQL
  → Catalog record is persisted centrally

User B opens Catalog
  → Kairos API queries same Supabase PostgreSQL
  → RLS checks User B’s workspace/permissions
  → User B sees the asset only if authorized
```

If User B already has the Catalog page open, you can optionally do:

```text
Supabase Realtime detects INSERT on kairos_assets
  → Notifies subscribed clients
  → Frontend refetches catalog or updates the affected row
```

## Important security rule

“Every user sees the change” must **not** mean every user sees every asset.

Use Supabase RLS:

```sql
create policy assets_select_for_workspace_members
on kairos_assets
for select
to authenticated
using (
  exists (
    select 1
    from kairos_workspace_members m
    where m.workspace_id = kairos_assets.workspace_id
      and m.user_id = auth.uid()
  )
);
```

So:

```text
User A imports asset into Workspace A
  → User A sees it
  → Workspace A members see it if permitted
  → Workspace B users do not see it
  → Anonymous users do not see it
```

Supabase recommends RLS for every table reachable by browser/mobile clients, and warns that the service-role/secret key bypasses RLS and must remain server-side only. [supabase](https://supabase.com/docs/guides/getting-started/the-supabase-way-to-build)

## What this means for Kairos

Use this wording:

> **Kairos uses Supabase-hosted PostgreSQL as its central authoritative database. Metadata ingested by one authorized user is persisted centrally and becomes visible to other authorized users according to workspace membership and Row Level Security. Supabase Realtime may optionally notify open clients of changes, but authorization is always enforced server-side.**

Do not say:

> “Supabase automatically shares all data with all users.”

That would be a security mistake.

## Practical demo behavior

For your demo:

1. User A imports a dbt manifest or OpenLineage event.
2. Kairos writes assets, lineage, and evidence to Supabase PostgreSQL.
3. User A sees the new asset immediately.
4. User B refreshes Catalog—or, if Realtime is enabled, sees it update automatically.
5. User B can open the same asset only if they belong to the same workspace and have permission.
6. A user from another workspace cannot see it.

That is the correct enterprise behavior: **central persistence, shared but permission-scoped visibility, and optional realtime UI updates.**

## How evidence works across different sources

Evidence is not “SQL lineage.” Evidence is any **verifiable observation, declaration, parse result, classification, or execution record** that explains why Kairos believes something about an asset, relationship, quality state, or AI answer. The same evidence model must work for SQL, files, GitHub repositories, databases, dbt, OpenLineage, ML models, and RAG.

OpenLineage provides the best reference model: it separates a **job**, a **run**, a **dataset**, and extensible **facets**. A facet is atomic metadata attached to a run, job, or dataset; it carries context such as what ran, how it ran, what was used, and what was produced. [openlineage](https://openlineage.io/docs/spec/facets/)

## Core principle

Kairos should never store only a lineage arrow. Every edge, classification, quality result, preview, or AI answer should have an evidence record:

```text
Raw source artifact
  → normalized evidence
  → canonical asset / relationship
  → reasoning state
  → UI explanation
```

A relationship is not automatically true because two assets exist. It becomes:

- `OBSERVED` only when runtime evidence supports it.
- `POSSIBLE` when static analysis or a declaration supports it.
- `REFUTED_FOR_RUN` only when complete negative evaluation exists for that run.
- `UNKNOWN` when evidence is absent, incomplete, or ambiguous. 

## Evidence model by source type

| Source | What evidence it provides | What it can prove | What it cannot prove | Kairos evidence state |
| --- | --- | --- | --- | --- |
| SQL file / SQLGlot | Parsed tables, columns, joins, CTEs, transformations | Static dependency is plausible | That a particular run executed or propagated the dependency | `POSSIBLE` |
| dbt `manifest.json` | Declared model/source/exposure dependencies, tests, descriptions | A dbt model declares a dependency | That a production run executed or that data propagated | `POSSIBLE` / declared |
| dbt `run_results.json` | Test execution outcomes | A test passed/failed for a run | Complete column-level runtime propagation | `OBSERVED` for the test result |
| OpenLineage run event | Job, run, inputs, outputs, timing, status, facets | A job read/wrote datasets during a run | A direct edge from every input to every output unless lineage facet says so | `OBSERVED` for run boundary |
| OpenLineage lineage facet | Explicit dataset/job/field lineage | Exact declared or observed lineage edges | Completeness of instrumentation | `OBSERVED` for supplied edge |
| PostgreSQL catalog | Tables, columns, types, constraints, comments | Structural metadata exists | Data content, runtime usage, lineage | Structural metadata only |
| PostgreSQL query log | Queries executed against source | A query referenced certain tables/columns | Full column-level propagation unless query/log parser supports it | `OBSERVED` query reference / `POSSIBLE` lineage |
| GitHub repository | Repo, branch, commit, file tree, file content | A file exists at a commit | That SQL was executed or that dbt models ran | File-existence evidence |
| Local file upload | User-supplied JSON/CSV/document metadata | User supplied this artifact | Source authenticity or live connectivity | User-supplied evidence |
| Image metadata | MIME type, dimensions, hash, path | File metadata exists | Image content meaning, lineage, quality | Metadata evidence |
| MLflow | Model version, training run, parameters, metrics, artifacts | A model version exists and was trained from recorded inputs | That every feature contributed at inference | `OBSERVED` training lineage |
| RAG trace | Query, retrieved chunks, prompt, model, answer, tokens | What the AI system retrieved and generated | That the answer is correct or grounded without evaluation | `OBSERVED` trace |
| Manual steward action | Human classification/approval | A human made a decision | That the decision is technically correct | Manual evidence |
| Profiler | Row count, null rate, distinct count, distribution | Statistical profile at a time | Complete data quality or lineage | `OBSERVED` profile |

## Evidence record contract

Every source should normalize into one common evidence shape.

```json
{
  "evidence_id": "uuid",
```

## How each source becomes evidence

### 1. SQL file

```text
User uploads query.sql
  → SQLGlot parses SQL
  → Extract tables, columns, joins, aliases
  → Create relationship candidates
  → Store parsed SQL + extraction span
  → Mark lineage POSSIBLE
```

Example:

```sql
SELECT
  o.customer_id,
  c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id;
```

Evidence:

| Field | Value |
| --- | --- |
| Source | SQL file |
| Parser | SQLGlot |
| Subject | `analytics.customer_360.email` |
| Related subject | `customers.email` |
| Relationship | Column lineage |
| State | `POSSIBLE` |
| Reason | Static SQL analysis found a mapping |
| Cannot prove | That this query ran or that the value propagated in a production run |

### 2. dbt manifest

```text
User uploads manifest.json
  → Parse nodes, sources, exposures, tests
  → Create dbt model/source/exposure assets
  → Create declared depends_on relationships
  → Store manifest version and node unique_id
  → Mark lineage declared / POSSIBLE
```

Example:

```json
{
  "unique_id": "model.finance.fct_revenue",
  "depends_on": {
    "nodes": ["model.finance.stg_orders"]
  }
}
```

Evidence:

| Field | Value |
| --- | --- |
| Source | dbt manifest |
| Subject | `model.finance.fct_revenue` |
| Related subject | `model.finance.stg_orders` |
| Relationship | Declared model dependency |
| State | `POSSIBLE` |
| Reason | Declared in dbt manifest |
| Cannot prove | That the model ran or that rows propagated |

If a dbt test result is ingested, that result is separately `OBSERVED` evidence for the test outcome—not proof of full column-level propagation.

### 3. OpenLineage event

```text
Pipeline emits OpenLineage event
  → Kairos stores immutable raw event
  → Parses job, run, inputs, outputs, facets
  → Creates job/run/dataset records
  → Creates run-boundary relationships
  → Uses lineage facet for exact edges if present
  → Marks event-backed relationships OBSERVED
```

OpenLineage explicitly warns against creating a Cartesian product from every event input and output. A job reading `customers` and `orders` and writing `customer_summary` and `order_summary` does not imply four lineage edges; the Lineage Job Facet records the actual edges. [openlineage](https://openlineage.io/docs/1.48.0/)

Evidence:

| Field | Value |
| --- | --- |
| Source | OpenLineage |
| Run ID | Run UUID |
| Subject | Output dataset |
| Related subject | Exact input dataset from lineage facet |
| Relationship | Runtime job lineage |
| State | `OBSERVED` |
| Reason | Observed during run |
| Cannot prove | Column propagation unless field-level facet exists |

### 4. PostgreSQL catalog discovery

```text
User connects read-only PostgreSQL role
  → Kairos queries information_schema / pg_catalog
  → Reads schemas, tables, columns, constraints
  → Creates structural assets
  → Stores discovery-run provenance
  → Marks metadata OBSERVED
```

Evidence:

| Field | Value |
| --- | --- |
| Source | PostgreSQL catalog |
| Subject | `analytics.orders` |
| Evidence kind | Structural metadata |
| State | `OBSERVED` |
| Proves | Table/column metadata existed at discovery time |
| Cannot prove | Lineage, data quality, usage, or runtime behavior |

A PostgreSQL connection gives Kairos **metadata access**, not automatic query-log access or data-preview access. Those require separate permissions.

### 5. GitHub repository

```text
User connects GitHub
  → Grants repository-scoped read access
  → Kairos reads repo tree at a commit
  → Discovers .sql, .yml, manifest.json, OpenLineage files
  → Stores commit SHA, path, file hash
  → Runs SQL/dbt/OpenLineage parsers only on relevant files
  → Creates file assets and parser-derived evidence
```

Evidence:

| Field | Value |
| --- | --- |
| Source | GitHub |
| Subject | `repo://org/repo/path/models/stg_orders.sql` |
| Commit | `abc123` |
| Evidence kind | File existence / parsed SQL |
| State | File existence `OBSERVED`; parsed lineage `POSSIBLE` |
| Cannot prove | That the SQL ran in a warehouse |

A GitHub connection proves repository access and file discovery. It does not automatically prove database lineage.

### 6. Local file upload

```text
User uploads JSON / CSV / document / image
  → Browser sends authorized file
  → Backend validates type/size/schema
  → Stores raw artifact or metadata reference
  → Extracts safe metadata
  → Creates file/document/image asset
  → Marks evidence as user-supplied
```

Evidence:

| Source | Evidence produced | State |
| --- | --- | --- |
| JSON metadata | Structural metadata and explicit relationships | `OBSERVED` for user-supplied fact |
| CSV | File metadata; profile only if parsing is implemented | File metadata `OBSERVED`; profile `UNKNOWN` unless run |
| Document | Path, MIME type, size, extracted text if implemented | Metadata `OBSERVED`; semantics `UNKNOWN` |
| Image | MIME type, dimensions, hash, thumbnail if available | Metadata `OBSERVED`; content meaning `UNKNOWN` |

A file import must never be described as a live connector.

### 7. MLflow / ML metadata

```text
MLflow emits or exposes training run
  → Kairos ingests model version, run ID, parameters, metrics, artifacts
  → Links training dataset(s), feature views, code version
  → Creates model/training/feature lineage
  → Marks training lineage OBSERVED
```

Evidence:

| Field | Value |
| --- | --- |
| Source | MLflow |
| Subject | `model.churn_classifier@v7` |
| Related subject | `feature.customer_lifetime_value` |
| Relationship | Feature-to-model training lineage |
| State | `OBSERVED` |
| Proves | Model version recorded this feature/training dataset |
| Cannot prove | That the feature contributed to every inference |

### 8. RAG trace

```text
User asks Kairos a question
  → Kairos retrieves metadata chunks
  → Kairos records retrieved context, prompt, model, answer
  → Kairos evaluates grounding/citations
  → Stores RAG trace
  → Marks retrieval/generation OBSERVED
  → Marks correctness UNKNOWN until evaluated
```

Evidence:

| Field | Value |
| --- | --- |
| Source | Kairos RAG |
| Subject | RAG answer / trace |
| Related subject | Retrieved asset/column/policy chunks |
| Evidence kind | AI retrieval and generation trace |
| State | Retrieval `OBSERVED`; factual correctness `UNKNOWN` until evaluated |
| Cannot prove | Answer correctness without evaluation |

## How the four states work per source

| Situation | Correct state |
| --- | --- |
| OpenLineage lineage facet says output field derives from input field | `OBSERVED` |
| SQLGlot finds a likely dependency | `POSSIBLE` |
| dbt manifest declares a dependency | `POSSIBLE` / declared |
| User manually creates a relationship | `OBSERVED` as a manual declaration, but not runtime-observed |
| Run event confirms a job read/wrote datasets | `OBSERVED` for run boundary |
| Run had complete observation coverage and proved no contribution | `REFUTED_FOR_RUN` |
| Runtime event is missing | `UNKNOWN` or `POSSIBLE`, never `REFUTED_FOR_RUN` |
| Parser cannot understand SQL | `UNKNOWN` |
| Source connection failed | Evidence unavailable; do not invent state |
| PII classification is manually applied | `OBSERVED` manual classification |
| PII classification is inferred from lineage | `POSSIBLE` or inherited classification, with provenance |

## How PII evidence works

PII is not only a tag. It is an evidence-backed classification with a propagation path.

```text
customers.email = PII_SOURCE
        │
        ▼
stg_customers.email = PII_INHERITED
        │
        ▼
dim_customer.email_masked = PII_MASKED
        │
        ▼
marketing_extract.email = PII_POTENTIAL
```

| Evidence type | Example | State |
| --- | --- | --- |
| Manual classification | Steward tags `customers.email` as PII | `OBSERVED` manual classification |
| Lineage propagation | Column lineage shows direct copy | `OBSERVED` inherited classification |
| Static SQL inference | SQLGlot finds possible mapping | `POSSIBLE` inherited classification |
| Masking transformation | Hash/mask function detected | `PII_MASKED` |
| Missing lineage | Downstream file has no column mapping | `UNKNOWN` |
| Aggregation with no identifiers | Count only, no direct PII field | Potential `PII_CLEARED`, requires review |

Atlan and DataHub both describe lineage-based PII propagation: a PII classification at source can propagate to derived columns through joins, transformations, and aggregations.

## Kairos implementation rule

For every source, implement this same five-step pipeline:

```text
1. Capture raw artifact/event
2. Preserve provenance and immutable raw record
3. Normalize into source-neutral evidence
4. Resolve canonical asset/relationship identity
5. Derive four-state conclusion without using ground truth
```

Then the UI must always answer:

```text
What do we know?
How do we know it?
When did we learn it?
For which run or time period?
What remains unknown?
```

That is how evidence remains consistent whether the input is SQL, a GitHub file, a PostgreSQL catalog, an image, a dbt manifest, an OpenLineage event, an ML model, or a RAG answer.




# Competitor authentication, access, and metadata-capture workflow analysis

## Executive answer

Competitors do **not** ask users to give a metadata platform unrestricted access to their private systems. They use a scoped, source-specific credential or OAuth authorization; the platform authenticates to the source, discovers only permitted metadata, normalizes it into its own catalog, and then controls which human users can see that metadata through platform roles, personas, workspaces, or row-level policies. For Kairos, the correct model is: **Kairos user identity is separate from source credentials; source credentials authorize Kairos to read a narrowly scoped source; Kairos RLS/authorization controls which Kairos user can view the resulting metadata.** [docs.atlan](https://docs.atlan.com/product/connections/references/connector-auth-and-setup)

## 1. The universal competitor workflow

```text
1. User signs up / signs in to the metadata platform
2. User creates a source connection
3. User chooses an authentication method
4. User grants only the required source scope
5. Platform validates the credential/connection
6. Platform runs discovery / ingestion
7. Platform reads only permitted metadata
8. Platform stores raw evidence and normalized catalog records
9. Platform applies its own user/tenant permissions to catalog visibility
10. User browses assets, lineage, quality, and incidents inside the platform
```

The critical separation is:

| Concept | Question answered | Example |
| --- | --- | --- |
| Authentication | Who is calling? | Kairos user JWT, GitHub token, database user |
| Source authorization | What can Kairos read from the user’s source? | Read-only PostgreSQL metadata, GitHub repository contents |
| Platform authorization | Which Kairos assets can this user see? | Finance-domain assets only |
| Tenant isolation | Which organization’s records are visible? | Tenant A cannot see Tenant B |
| Source scope | Which repositories/schemas/databases were selected? | Only `repo-x`, only `sales` schema |
| Evidence visibility | Who may inspect raw events or sensitive metadata? | Steward/admin only |

## 2. DataHub workflow

### User sign-up and platform access

DataHub authenticates user and service requests through its metadata service using JWT bearer tokens. It supports native DataHub tokens and JWTs issued by external OAuth2/OIDC providers such as Okta, Auth0, and Azure AD. [docs.datahub](https://docs.datahub.com/docs/authentication)

```text
User signs in
  → DataHub issues/accepts a JWT
  → Frontend sends Authorization: Bearer <token>
  → DataHub metadata service authenticates request
  → Platform policies determine accessible assets/actions
```

DataHub also supports **service accounts** for non-human identities such as ingestion pipelines and CI/CD. An administrator creates a service account, generates a time-limited access token, and can revoke it later. The token is shown once and must be stored securely. [docs.datahub](https://docs.datahub.com/docs/features/feature-guides/service-accounts)

### How a user connects a source

In DataHub’s UI ingestion flow, the user creates an ingestion source, completes a connection form, and can reference encrypted secrets rather than entering raw credentials directly. Secret fields are resolved by a trusted worker at job time; secrets are decrypted server-side and sent to the worker over TLS. [docs.datahub](https://docs.datahub.com/docs/ui-ingestion)

```text
User opens Ingestion
  → Chooses source type
  → Enters host/database/project details
  → Selects or creates a managed secret
  → Tests connection
  → Saves ingestion recipe
  → Runs or schedules ingestion
```

### What DataHub accesses

DataHub reads metadata under the permissions of the configured source credential. For example, a source integration may read database catalogs, schemas, tables, columns, query logs, dashboards, or pipeline metadata—but only what that credential is authorized to access. The exact capability depends on the connector and source permissions. [docs.datahub](https://docs.datahub.com/docs/ui-ingestion)

### Kairos adaptation

| DataHub pattern | Kairos implementation |
| --- | --- |
| JWT-based platform authentication | Supabase Auth JWT for every Kairos user request |
| Service accounts | Kairos connector/worker identity for scheduled ingestion |
| Secret references | Store source credentials server-side; never expose them to the browser |
| Trusted worker resolves secrets | Hatchable/Node backend worker accesses credentials only during ingestion |
| Source-specific connector forms | PostgreSQL, GitHub, dbt, OpenLineage forms with different fields |
| Separate catalog search and graph traversal | Keep `/search`, asset lookup, and lineage traversal distinct |

## 3. OpenMetadata workflow

### User sign-up and access

OpenMetadata uses services, users, teams, roles, domains, policies, and bots/service identities. A user first configures a **service connection**, tests it, saves it, and then creates an ingestion workflow. [openmetadatastandards](https://openmetadatastandards.org/schemas/entity/services/)

```text
User signs in
  → Creates or selects a service
  → Configures source connection
  → Tests connection
  → Saves service
  → Creates ingestion workflow
  → Runs/schedules ingestion
  → Views resulting assets
```

OpenMetadata documents that credentials can be handled through the ingestion workflow, and that existing services use stored credentials rather than credentials supplied in each new YAML run. Credential updates occur through the UI or API. [docs.open-metadata](https://docs.open-metadata.org/v2.0.x/deployment/ingestion/external/credentials)

### How a user connects a source

For a database such as Snowflake, the user supplies account, warehouse, database, schema, and authentication details. OpenMetadata supports basic auth, key-pair auth, and SSO depending on the source. It then asks the user to test the connection and save it. [docs.open-metadata](https://docs.open-metadata.org/v1.13.x/connectors/database/snowflake)

For BigQuery, OpenMetadata supports service-account key values, key-file paths, workload identity federation, and Application Default Credentials. After the service connection is created, ingestion can begin. [docs.open-metadata](https://docs.open-metadata.org/v2.0.x/connectors/database/bigquery)

### What OpenMetadata accesses

The connector account needs only metadata-read privileges. For Snowflake, OpenMetadata documents that a metadata-ingestion user needs `USAGE` on warehouse/database/schema and `SELECT` on tables; it does not require write access to the source. [docs.open-metadata](https://docs.open-metadata.org/v1.13.x/connectors/database/snowflake)

For Pub/Sub, OpenMetadata requires permissions to list and read topics/subscriptions, and recommends a viewer role rather than broad admin access. [docs.open-metadata](https://docs.open-metadata.org/v2.1.x-SNAPSHOT/connectors/messaging/pubsub)

### Kairos adaptation

| OpenMetadata pattern | Kairos implementation |
| --- | --- |
| Service connection object | `kairos_connections` table |
| Connection test | `/api/v1/connections/:id/test` |
| Ingestion workflow | `kairos_ingestion_runs` |
| Stored credentials | Server-side encrypted secret reference |
| Source-specific permission requirements | Connector capability registry |
| Scheduled ingestion | Durable job queue / scheduled worker |
| Capability-specific asset tabs | Backend capability registry |

## 4. Atlan workflow

### User sign-up and access

Atlan separates identity and access management into SSO/SCIM, users, groups, roles, personas, purposes, connection access, visibility, and audit logs. [docs.atlan](https://docs.atlan.com/product/capabilities/governance/access-control)

```text
User signs in through SSO
  → User receives a persona/role
  → Persona grants access to connections/domains/assets
  → Connection admin controls connection-level access
  → User sees only permitted metadata
```

A connection admin or workspace admin assigns additional connection admins. API tokens must be associated with personas to access connection assets. [docs.atlan](https://docs.atlan.com/faq/user-management-and-access-control)

### How a user connects a source

Atlan’s connector setup reference separates authentication methods, grants, network prerequisites, and scoping limits. It recommends service principals or managed identities backed by a secret store over long-lived keys or plaintext credentials. Credentials may be stored in Atlan or fetched from AWS Secrets Manager or GCP Secret Manager. [docs.atlan](https://docs.atlan.com/product/connections/references/connector-auth-and-setup)

For Redshift, Atlan supports basic username/password, IAM user, or IAM role authentication. It instructs users to create a read-only database user and grant schema-level `USAGE` permissions before configuring the crawler. [docs.atlan](https://docs.atlan.com/apps/connectors/data-warehouses/amazon-redshift/how-tos/set-up-access-and-authentication)

### What Atlan accesses

Atlan states that it reads **metadata, not production data**, under the service principal’s scope; data preview can be disabled centrally. [docs.atlan](https://docs.atlan.com/product/connections/references/connector-auth-and-setup)

This is an important product boundary for Kairos:

```text
Metadata access = schemas, tables, columns, lineage, ownership, documentation
Data access = row-level content, previews, profiling
```

Kairos should make these separate permissions.

### Kairos adaptation

| Atlan pattern | Kairos implementation |
| --- | --- |
| Personas | Kairos roles: viewer, steward, editor, admin |
| Purposes | Purpose-based access rules for sensitive metadata |
| Connection admins | Connection owner / connector admin |
| Secret-manager integration | Server-side secret reference; no plaintext credentials in DB/API responses |
| Metadata-only access posture | Default connector scope is metadata read, not data read |
| Preview opt-out | Separate `metadata:read` and `data:preview` permissions |

## 5. GitHub access workflow

### Recommended Kairos model

For Kairos, use a **GitHub App installation** for the production path and a **fine-grained personal access token** only as a lower-friction MVP fallback.

### GitHub App flow

```text
User signs in to Kairos
  → Clicks “Connect GitHub”
  → GitHub asks which account/organization to install the app on
  → User selects specific repositories
  → User approves requested permissions
  → GitHub issues an installation ID
  → Kairos exchanges/uses installation credentials
  → Kairos reads only selected repository metadata/files
  → User can revoke installation in GitHub
```

GitHub Apps have no permissions by default. The app requests only the minimum repository, organization, enterprise, or account permissions it needs; users grant those permissions when installing the app. [docs.github](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)

GitHub recommends minimum permissions, limiting repository access, subscribing only to required webhooks, and verifying webhook signatures with a webhook secret. [docs.github](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)

### Fine-grained PAT fallback

A fine-grained PAT is limited to one user or organization and can be restricted to selected repositories and specific permissions. GitHub recommends choosing minimal repository access and minimal permissions. [docs.github](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

```text
User creates fine-grained PAT
  → Selects “Only select repositories”
  → Selects Kairos demo repository
  → Grants Contents: Read-only
  → Pastes token into Kairos connection form
  → Kairos stores it server-side
  → Kairos reads repository tree/files
```

A classic PAT can access every repository the token owner can access, which is why it should not be Kairos’s preferred model. [docs.github](https://docs.github.com/api/article?pathname=/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

### What Kairos should request

| Permission | Level | Purpose |
| --- | --- | --- |
| Metadata | Read | Repository metadata, default branch |
| Contents | Read | Read selected SQL/dbt/OpenLineage files |
| Webhooks | Read/write only if incremental sync is implemented | Receive push events |
| Administration | None | Not needed |
| Actions | None | Not needed |
| Secrets | None | Never request |

Kairos must not request write access merely to catalog a repository.

### Revocation behavior

If the user revokes the GitHub App installation or deletes the PAT:

```text
Next connection health check fails
  → Kairos marks connection REVOKED / CREDENTIALS_EXPIRED
  → Existing imported metadata remains as historical evidence
  → No new discovery/sync is attempted
  → User may delete imported data or retain it according to retention policy
```

## 6. PostgreSQL source-access workflow

### Recommended Kairos model

Kairos should connect to a user’s PostgreSQL database using a **dedicated read-only Kairos user**, not the user’s admin account.

```sql
CREATE ROLE kairos_reader LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE app_db TO kairos_reader;

GRANT USAGE ON SCHEMA analytics TO kairos_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO kairos_reader;

-- Metadata-only access can be narrower:
GRANT USAGE ON SCHEMA information_schema TO kairos_reader;
GRANT SELECT ON information_schema.tables TO kairos_reader;
GRANT SELECT ON information_schema.columns TO kairos_reader;
```

This follows the same least-privilege pattern used by OpenMetadata and Atlan: grant `USAGE` on relevant schemas and read access only to the metadata needed. [docs.open-metadata](https://docs.open-metadata.org/v1.13.x/connectors/database/snowflake)

### What Kairos should read

| Capability | Required source permission | Kairos feature |
| --- | --- | --- |
| List schemas/tables/views | Catalog metadata read | Catalog discovery |
| Read columns/types/nullability | Catalog metadata read | Schema tab |
| Read primary/foreign keys | Catalog metadata read | Relationship candidates |
| Read comments | Column/table comment read | Descriptions |
| Read table statistics | Optional elevated permission | Profiling hints |
| Read query logs | Separate elevated permission | Runtime lineage candidates |
| Execute data queries | Separate explicit permission | Preview/profiling only |

Kairos must distinguish:

```text
Catalog discovery ≠ query execution
Query execution ≠ query-log capture
Query-log capture ≠ complete runtime lineage
```

### Connection flow

```text
User creates PostgreSQL connection
  → Supplies host, port, database, username, password/SSL config
  → Kairos stores secret server-side
  → Kairos tests connection
  → Kairos checks metadata permissions
  → User selects schemas/databases to catalog
  → Kairos runs discovery
  → Kairos normalizes tables/columns
  → Kairos persists assets and provenance
  → User browses catalog
```

## 7. Supabase / Kairos platform authorization

Kairos’s own users should be authenticated with Supabase Auth. Supabase issues signed JWTs containing identity and authorization claims; these JWTs are the foundation for PostgreSQL Row Level Security. [supabase](https://supabase.com/docs/guides/auth)

```text
User signs in to Kairos
  → Supabase Auth issues JWT
  → Browser sends JWT with API request
  → API validates JWT
  → API queries using user-scoped client
  → PostgreSQL RLS filters rows
  → User sees only authorized metadata
```

Supabase distinguishes:

| Role | Meaning | Security rule |
| --- | --- | --- |
| `anon` | Unauthenticated request | Only public data, if intentionally public |
| `authenticated` | Signed-in user | RLS policies apply |
| `service_role` / secret key | Server-side privileged access | Bypasses RLS; never expose to browser |

Supabase explicitly warns that service-role/secret keys bypass RLS and must remain server-side. [supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)

### Kairos RLS model

```sql
-- Tenant/workspace membership
create table kairos_workspace_members (
  workspace_id uuid not null,
  user_id uuid not null,
  role text not null,
  primary key (workspace_id, user_id)
);

-- Asset isolation
alter table kairos_assets enable row level security;

create policy assets_select_for_members
on kairos_assets
for select
to authenticated
using (
  exists (
    select 1
    from kairos_workspace_members m
    where m.workspace_id = kairos_assets.workspace_id
      and m.user_id = auth.uid()
  )
);
```

Do not rely on `user_metadata` JWT claims for authorization, because authenticated users may be able to modify that metadata. Supabase explicitly warns against relying on user-metadata claims in RLS policies. [supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 8. How PII access should work

PII classification and PII access must be separated.

```text
PII classification = metadata about sensitivity
PII access = permission to view sensitive values/content
```

| Action | Required permission |
| --- | --- |
| See that a column is tagged PII | `metadata:read` |
| See PII classification provenance | `governance:read` |
| Change PII classification | `governance:classify` |
| View raw sample data | `data:preview` |
| View unmasked PII | `data:pii:unmasked` |
| Trigger masking policy | `governance:policy:apply` |
| View PII lineage path | `lineage:read` |

Atlan’s model is useful here: governance classifications such as PII propagate along lineage, while access enforcement is handled through personas, purposes, and connection access. 

Kairos should therefore propagate a PII classification through lineage, but not automatically grant users access to the underlying sensitive data.

## 9. Conflict prevention: user authorization vs source authorization

This is the central conflict you identified.

```text
User says: “Kairos may read my GitHub repository.”
≠
User says: “Every Kairos user may see my repository metadata.”
```

Correct separation:

```text
Source credential
  → authorizes KAIROS BACKEND to read SOURCE

Kairos role / workspace membership
  → authorizes a KAIROS USER to view CATALOG METADATA

Source scope
  → limits WHICH repositories/schemas/databases are read

Evidence sensitivity
  → limits WHO may view raw events, previews, or PII-related metadata
```

Example:

| Situation | Correct behavior |
| --- | --- |
| User connects private GitHub repo | Only that user/workspace can see imported repo metadata |
| User connects PostgreSQL with read-only role | Kairos reads only permitted schemas |
| User has no `data:preview` permission | User sees schema/metadata but no row preview |
| Another workspace user has no membership | User cannot see the connection or its assets |
| Source credential expires | Connection becomes `CREDENTIALS_EXPIRED`; existing historical evidence may remain visible according to policy |
| PII source column propagates downstream | Downstream columns inherit classification, not automatic data access |
| RAG user asks about PII | Retrieval filters out metadata the user cannot access |

## 14. Demo-ready recommendation

For the first reliable Kairos demonstration, implement this exact access model:

1. User signs in with Supabase Auth.
2. User creates a connection.
3. Kairos stores only a server-side credential reference.
4. Kairos tests the connection separately from discovery.
5. Kairos runs discovery using a least-privilege source credential.
6. Kairos persists raw evidence, normalized assets, provenance, and connector status.
7. Kairos applies workspace membership and RLS before showing catalog/lineage/search results.
8. Demo fixtures are explicitly labeled and never silently used when a live source fails.
9. PII classification propagates through lineage, but PII data access remains separately authorized.
10. The UI never claims semantic search, grounded RAG, live lineage, or tenant isolation unless those paths have been tested end to end.

This gives Kairos the same security boundary as mature platforms—**scoped source access, server-side credential handling, platform-level authorization, and honest capability reporting**—without requiring a complex enterprise IAM system on day one.
